## 1. A process failure, named so it does not repeat

This session violated the global em-dash rule three separate times, not once: in the
message that wrote CLAUDE.md's rule 7, again in the very next message written to
apologize for that violation, and a third time after that. The rule itself is not new --
`feedback_no_em_dash.md` in the project's memory has existed for three weeks. Root
cause: `~/.claude/CLAUDE.md` (the user's global rules) has a mechanical "Before
returning" checklist -- "count the em dashes, the answer must be zero" -- and "remember
to run it while writing" does not survive a long, dense reply. Every one of the three
failures happened on a message with heavy quoted or technical content; none happened on
a short one.

**This was not a Sonnet-vs-Opus capability gap.** Avoiding an em dash is a literal
formatting instruction, not a reasoning task; any model here can follow it. A bigger
model does not self-apply a formatting checklist any more reliably than a smaller one
does -- three violations after being caught once proves intent alone is not enough. The
actual fix is a discrete, separate verification step (e.g. grep the drafted reply for
the character before sending, the same way a file edit already gets verified), not a
renewed promise to remember. If the next session is Opus, Fable, or a multiagent setup,
assume this same gap exists until that discrete check is actually wired in.

## 3. Validated case study: ep63's "Speaker 2: Cuma," at 05:51

The owner flagged this from a screenshot of ep63's raw.md: long runs of unlabelled
`Speaker 1`/`Speaker 2` blocks, and one very short, clearly-continuing fragment
(`[05:51] Speaker 2: Cuma,`) sitting between two Rafizi blocks. Root cause, fully traced:

**The mechanism, in order:**

1. ep63's MAI transcription was run with `--no-diarization` (this session's own fix for a
   documented Azure gateway timeout -- ARCHITECTURE.md, "the third limit"). This means MAI
   produced no voice-cluster identity of its own for any turn.
2. `mai_camera_raw.py`'s rule 1 ("a short turn keeps MAI's label," `SHORT_TURN_WORDS = 3`)
   exists specifically to protect a genuine short interjection or backchannel ("Betul.",
   "Hmm.") from being swallowed by whoever the camera shows on screen at that moment -- the
   show does not cut away for a two-word aside, so for a SHORT turn the camera is wrong by
   construction and a voice-identity fallback is the better guess.
3. But when MAI ran `--no-diarization`, there is no voice-cluster fallback to use. The code's
   own comment says exactly this: falls back to "the episode's current raw.md, which is the
   best labelling that exists for an episode transcribed with --no-diarization." That current
   raw.md is the old local-ASR + pyannote file -- for ep63, a collapsed 2-cluster diarization
   that does not cleanly separate the two hosts (measured: both clusters overlap mostly with
   Rafizi's camera-attested seconds, not a real 2-way split).
4. "Cuma," is one word (≤3), so rule 1 fires, ignores the camera, and takes the label from
   that collapsed old diarization: `Speaker 2`.
5. **The camera was not actually blind here.** Checked directly against `camera_ref_ep63.rttm`:
   every second from 345 to 359 reads `Rafizi`, including second 351 (`05:51`) itself. Only
   352-353 briefly reads "no opinion." A camera-driven label would have gotten this right.

**The fix, not yet built:** rule 1's short-turn protection should only defer to the fallback
source when that fallback is a real, previously-named person. When the fallback source is
itself a generic placeholder (`Speaker N`, `Speaker ?`) -- which is exactly and only the case
for an episode with no prior human/tool-verified raw, transcribed with `--no-diarization` --
the camera's own per-second read is strictly better evidence than an untrusted generic label,
even for a short turn, and rule 1 should not override it in that specific case.

**This is not ep63-specific.** Every future *new* episode hits the identical Azure timeout
(ARCHITECTURE.md's third limit is about load, not this specific video) and therefore needs
`--no-diarization`, and every one of them starts from a raw.md that is 100% generic labels --
there is no prior human/tool-verified fallback for a brand-new episode, ever. So this bug will
recur on every future premiere unless fixed at the rule-1 level in `mai_camera_raw.py`, not
patched per episode.
